# 任务列表：[功能名称]

**输入**：来自 `/specs/[###-feature-name]/` 的设计文档

**前置条件**：plan.md（必填）、spec.md（用户故事必填）、research.md、data-model.md、contracts/

**测试**：下文示例含测试任务。测试为**可选**——仅当功能规格明确要求时才纳入。

**组织方式**：按用户故事分组，便于各故事独立实施与测试。

## 格式：`[ID] [P?] [Story] 描述`

- **[P]**：可并行（不同文件、无依赖）
- **[Story]**：所属用户故事（如 US1、US2、US3）
- 描述中须包含确切文件路径

## 路径约定

- **Spring Boot（宪法默认）**：`src/main/java/.../{controller,service,repository,entity}/`、
  `src/main/resources/`、`src/test/java/`
- **前后端分离**：API 在 `backend/src/main/java/...`；前端单独目录
- 下文路径假定 Spring Boot 单模块——包名根路径以 plan.md 为准

## 依赖与执行顺序

### 阶段依赖

- **阶段 1（搭建）**：无依赖，可立即开始
- **阶段 2（基础设施）**：依赖阶段 1 完成 — **阻塞**所有用户故事
- **阶段 3+（用户故事）**：均依赖阶段 2 完成
  - 之后可按人力并行，或按 P1 → P2 → P3 顺序执行
- **收尾阶段**：依赖所有目标用户故事完成

### 用户故事间依赖

- **用户故事 1（P1）**：阶段 2 完成后即可开始，不依赖其他故事
- **用户故事 2（P2）**：阶段 2 完成后即可开始，可与 US1 集成但须可独立测试
- **用户故事 3（P3）**：阶段 2 完成后即可开始，可与 US1/US2 集成但须可独立测试

### 单条用户故事内部顺序

- 若含测试：先写测试并确认失败，再实现
- 先实体，再 Service，再接口
- 先核心实现，再集成
- 当前故事完成后再进入下一优先级

### 并行机会

- 阶段 1 中标记 [P] 的任务可并行
- 阶段 2 中标记 [P] 的任务可并行
- 阶段 2 完成后，各用户故事可并行（视人力而定）
- 同一故事内标记 [P] 的测试可并行
- 同一故事内标记 [P] 的实体可并行
- 不同开发者可并行不同用户故事

## 实施策略

### 优先 MVP（仅用户故事 1）

1. 完成阶段 1：搭建
2. 完成阶段 2：基础设施（**关键** — 阻塞所有故事）
3. 完成阶段 3：用户故事 1
4. **停止并验证**：独立测试用户故事 1
5. 就绪后部署/演示

### 增量交付

1. 完成搭建 + 基础设施 → 基础就绪
2. 增加用户故事 1 → 独立测试 → 部署/演示（MVP）
3. 增加用户故事 2 → 独立测试 → 部署/演示
4. 增加用户故事 3 → 独立测试 → 部署/演示
5. 每个故事增量交付，不破坏已有故事

### 多人并行策略

多名开发者时：

1. 共同完成搭建 + 基础设施
2. 基础设施完成后：
   - 开发者 A：用户故事 1
   - 开发者 B：用户故事 2
   - 开发者 C：用户故事 3
3. 各故事独立完成与集成

## 备注

- [P] 表示不同文件、无依赖，可并行
- [Story] 标签用于将任务映射到用户故事，便于追溯
- 每个用户故事应可独立完成与测试
- 实施前确认测试失败（若含测试）
- 每完成一个任务或逻辑组即可提交
- 可在任一检查点暂停并单独验证该故事
- 避免：任务描述模糊、同文件冲突、破坏独立性的跨故事强依赖
